Chairman's Verdict

Decision Hybrid

Keep ScreenBuddy as the shipped product/legal name. Lead marketing and user-facing voice with Pesto as the character brand — the way Mailchimp's chimp isn't the company name.

Why reasoning

  • Renaming touches at least six live or half-live systems in the next 48 hours: an sk_live_ Stripe product, an appId tied to a local config file with no migration written, two Supabase projects, a Vercel backend URL, and a hardcoded support domain — while the git log shows a public beta launch already queued. That's a distributed-systems migration dressed as a find-and-replace.
  • "Zero customers so it's a 30-second edit" (the Expansionist's core claim) isn't credible — the prompt explicitly states the config change orphans existing installs without a migration, and a portable .exe is already built.
  • Against that concrete, deadline-incompatible cost, the case for Pesto is pure taste with no data behind it — no domain check, no trademark check, no user test. The burden of proof sits on the side proposing change, and it hasn't met that burden in a 2-day window.
  • But the brand critique isn't wrong — ScreenBuddy is generic, Pesto is the more distinctive, ownable asset, and it's already fully built (dialogue, art, personality) and completely decoupled from the risky infrastructure. The README already half-encodes this hybrid today: "ScreenBuddy (Pesto) — v1."

Blind Spots the Peer Review Caught emergent

  • Nobody checked the checkable unknowns. Every reviewer, across all 5 rounds, flagged that nobody spent the 15-30 minutes to check pesto.app/.com domain availability or the trademark/collision risk with the existing "Pesto" dev tool — cheap, fast, and would have resolved half the debate with data instead of narrative.
  • The hybrid path has a hidden cost nobody weighed. Shipping "Meet Pesto" marketing copy while the installer, appId, and billing descriptor still say ScreenBuddy creates a customer-facing inconsistency right at first install / first charge — the exact moment trust matters most.
  • "The infrastructure" isn't one risk tier. Stripe (real billing, real card statements) is categorically higher-stakes than Supabase/Vercel project names (purely cosmetic, freely renameable). No advisor separated these.
  • Nobody verified the actual Stripe mechanics. Product display names are typically just metadata, separate from the billing descriptor — meaning both "30-second edit" and "touching a live payment system" may be overstating or understating the real risk without anyone checking.
  • No advisor proposed a concrete trigger condition for revisiting later (e.g. "at 1,000 users" or "if a churn survey mentions confusion") — "revisit later" was left as a platitude that could recreate the same debate in six months.

The Recommendation do this

  • Make zero backend/infra changes today. Keep package.json, appId, the local config file, the live Stripe product, both Supabase projects, and the Vercel backend exactly as "ScreenBuddy."
  • Front-load Pesto in every not-yet-shipped user-facing surface: marketing site headline/hero ("Meet Pesto, your screen buddy"), onboarding flow, tray tooltip framing, README lead.
  • In parallel, spend 15-30 minutes checking pesto.app/.com domain availability and the competing "Pesto" dev tool's collision severity — so a future full rename, if it happens, is data-backed rather than vibes-backed.

Full advisor responses

The Expansionist — rename_to_pesto

Every dollar of "already-live infrastructure" you listed is trivially cheap to fix — a Vercel project rename, an appId string, a Stripe product name edit — because it's two days old with zero customers. The Stripe product literally has no subscribers yet; renaming it is a 30-second dashboard edit, not a migration. That's the entire cost side of the ledger. On the value side: you already built a mascot with personality, dialogue, and asset infrastructure, and you're about to spend your public beta launch — the one moment you get people's attention before they form a habit — reinforcing "ScreenBuddy," a name so generic it's functionally a category description, not a brand. "Screen buddy" is what a UX writer types into a placeholder before the real name gets decided. You cannot build a cult product, a devoted community, merch, a Discord full of inside jokes, on "ScreenBuddy." You can absolutely build all of that on Pesto. Nobody free-associates from "Slack" to "team chat" either — distinctive names are a feature, not a bug, and you fix the self-explanatory problem with a five-word tagline, not by neutering the name into oatmeal.

The Contrarian — keep_screenbuddy

Every argument for "Pesto" is a taste argument. Every argument against it is a Tuesday-you-ship-or-you-don't argument, and those always win two days out. Look at what "rename" actually touches: a live Stripe product real customers will see on their credit card statement, an appId change that orphans local config for anyone who already installed the exe today, two Supabase projects, a Vercel backend URL, a support domain already hardcoded into the app, and a git history that says "public beta marketing queue" — meaning you've already told people to expect something. That's not a find-and-replace, that's a migration project with a rollback plan, and you're proposing to start it 48 hours before launch. Meanwhile "Pesto" isn't even validated as a name — nobody's checked if pesto.app is taken, nobody's checked the other dev tool already using that name for trademark collision, nobody's confirmed the domain is buyable. You'd be trading a boring-but-shipped name for an exciting-but-unresearched one, on a deadline that has zero slack for "oh, pesto.com is squatted" or "turns out there's a pesto.dev already indexing above us." The mascot works exactly because it's decoupled from the infra — Pesto can be as charming as it wants in the UI copy while the plumbing underneath stays boring and already-paid-for. Ship what's built. Let the parrot be the parrot.

The Executor — hybrid

You have a sk_live_ Stripe product, two Supabase projects, a Vercel backend URL, an appId, and a built .exe all wired to "screenbuddy" — and a public beta commit already in the queue. Renaming means touching a live payment system and writing a config migration so existing installs don't lose settings, none of which is "48 hours" work if you actually test it, it's "48 hours of nothing else." That's not scope creep risk, that's scope creep certainty two days before launch. Meanwhile you already have the better brand asset sitting right there for free: Pesto is distinctive, memorable, and already has dialogue and art. So don't rename anything technical — keep package.json, appId, config file, Stripe product, Supabase, and the backend exactly as-is. Instead, front-load Pesto in every user-facing surface you haven't shipped yet: marketing site headline becomes "Meet Pesto, your screen buddy" instead of "ScreenBuddy," tray tooltip and onboarding copy lean on Pesto's personality, README flips to "Pesto by ScreenBuddy" if you want, and future URLs/handles you haven't registered yet (socials, support docs) can use Pesto. That's a copy and asset change you can finish today with zero backend risk. If Pesto proves itself as the brand people actually talk about, do the full legal/infra rename later as a deliberate v2 migration with a proper cutover plan, not as a launch-week fire drill.

The First Principles Thinker — hybrid

The question "rename or not" is downstream of an unasked question: what hypothesis does the name serve, and has it been tested? Nothing here shows Pesto vs ScreenBuddy was ever A/B'd with a user. This is a taste preference dressed as a strategy decision, and it's being entertained 48 hours before ship with a live Stripe SKU on the line. First principles: (1) a name's job is to be found, understood, and trusted — ScreenBuddy is doing job #1 and #2 for free, Pesto does neither without paid explanation; (2) the cost of the rename isn't "editing text," it's re-touching a live payment object, two Supabase projects, an appId tied to a config file on disk, and a domain that doesn't even exist yet (screenbuddy.app is referenced, pesto.app presumably isn't secured) — that's not a branding decision, that's a distributed-systems migration with a 2-day deadline; (3) the actual asset worth protecting is the mascot's personality, which is already decoupled from the infra and can be amplified without touching a single sk_live_ key. Ship the thing that's already wired to money, let the character do the brand work it's already doing for free, and revisit the corporate name after you have users and revenue data telling you the name is actually costing you conversions — not before.

The Outsider — keep_screenbuddy

I'm someone scrolling a landing page for two seconds before deciding whether to trust an app with screen access — the single biggest thing you can do for me is tell me what it does before I have to think. "ScreenBuddy" does that job instantly; "Pesto" makes me pause and Google it, and what I find is a pasta sauce and possibly a different dev tool, which is exactly the wrong instinct to trigger for something requesting screen-recording permissions. That confusion tax is a real cost even setting aside the fact that you'd be renaming a live Stripe subscription product real people are already being billed under, orphaning local config files, and re-registering a domain/support URL two days before you wanted to be in market — none of that is "just find and replace," it's the kind of yak-shave that eats your entire runway right when you need to be doing customer-facing work. The mascot angle is already free money you're not using: let Pesto stay the charming personality inside ScreenBuddy the same way Duolingo's owl or Mailchimp's chimp work — I bond with the character, I trust the plainly-named product, everybody wins. If in six months "Pesto" earns its keep as a beloved character with its own fandom, you can revisit a full rebrand with a real trademark search and a proper migration plan — not as a scramble on day minus-two.
